### 숨어 있던 세 번째 목적

`README.md`·`CLAUDE.md` 어디에도 없지만 실제로 존재하는 목적:

> **개발자 본인이 송이 공판 데이터를 분석하기 위한 도구.**

이것이 문서화되지 않아 검수 초안이 날씨 연동을 "사용자 요구 근거 없음"으로 잘못 판정했다.
본인 분석이 목적이라면 사용자 수요 근거는 애초에 불필요하고, 판단 기준은 **"분석 가설이 검증 가능한가"** 로 바뀐다.

세 번째 사용자로 명시할 것:

| 사용자 | 환경 | 니즈 | 성공 기준 |
|--------|------|------|-----------|
| 채취자·농가 | 모바일, 산지 | 오늘 내 지역 시세 | 구독 전환·재방문 |
| 조합 관계자·분석가 | PC | 시즌 통계·보고서 | 필터 적용률·내보내기 |
| **개발자 본인** | PC·로컬 | 데이터 탐색, 가설 검증 | **지표 아님 — 새 인사이트가 나오는가** |

세 번째 트랙은 SEO·리텐션 일정과 자원 경합만 관리하면 되고, 사용자 가치 기준으로 우선순위를 매길 대상이 아니다.

## 1. 핵심 결론 — 코어 밸류가 잘못 잡혀 있다 🔴

문답 중 나온 도메인 설명이 이 검수의 결론을 바꿨다.

> "시즌 중에는 매일 가격이 업데이트됨. 송이 공판 현황에 가격이 업데이트되면 **사용자가 직접 들어가기 전까지는 업데이트되었는지 알 수가 없음.**"

이것이 원본 사이트의 진짜 페인포인트다. 그렇다면:

- **대시보드·분석 도구 = 사용자가 들어온 *뒤*의 가치**
- **알림 = 사용자를 들어오게 만드는 가치 (= 미해결 문제 그 자체)**

현재 문서 체계는 이 관계가 뒤집혀 있다:

| | 알림 | 대시보드·분석 |
|---|---|---|
| `CLAUDE.md` 목적 | #2로 선언 | #1, #3 |
| README 주요 기능 | ❌ 없음 | ✅ 전면 |
| README 다음 단계 | ❌ 없음 | 부분 |
| 로드맵 우선순위 | 6순위 (최하위), "2주+, 별도 스프린트" | 1~5순위 |
| 구현 | ❌ 없음 (코드 확인 완료) | ✅ 완료 |

**즉, 제품이 원본 사이트 대비 확실히 우위인 유일한 지점이 미구현·미문서화 상태다.**
시각화 우위는 "이미 사이트에 들어온 사람"에게만 작동한다. 매일 들어가 보는 습관이 없는 사용자에게는 원본 사이트와 오송이가 동일한 마찰(직접 확인)을 갖는다.

여기에 실사용자 0명 + SEO 단독 유입이 겹치면 문제가 뚜렷해진다.
SEO는 사용자를 **한 번** 데려오고, 알림은 **매일** 데려온다. 첫 시즌 3개월 안에 리텐션을 만들지 못하면 다음 검증 기회는 1년 뒤다.

> **판단: 알림을 6순위 백로그가 아닌 시즌 전 필수 기능으로 승격.** 단, 아래 4장의 축소 범위로.

## 2. 최우선 리스크 — 데이터 권리 미확인 🔴

공개 서비스 + 권리 미확인 조합은 **다른 모든 작업의 전제를 무너뜨린다.** 시즌 직전에 중단 요청을 받으면 1년치 기회가 사라진다.

확인해야 할 것:

1. 산림조합중앙회 사이트 **이용약관**의 자동 수집·재배포 조항
2. `robots.txt` 의 크롤링 허용 범위
3. **공공데이터포털에 동일 데이터의 공식 개방 API가 있는지** — 있다면 크롤링을 대체해 리스크가 사라짐 (최선의 결과)
4. 매시간 접근이 상대 서버에 부담이 되는 수준인지

결과에 따른 대응:

| 결과 | 대응 |
|------|------|
| 공식 API 존재 | 파이프라인을 API로 전환. 리스크 해소 + 안정성 향상 |
| 허용 (출처 표기 조건 등) | README·화면 푸터에 근거·출처 명시 |
| 회색지대 | 수집 주기 완화, 출처·비상업 명시, 연락처 공개, 중단 요청 시 즉시 대응 방침 명문화 |
| 금지 | 서비스 공개 재검토 — **9월 전에 알아야 함** |

동시에 필요한 문서 항목 (현재 전부 없음):

- 면책: "표시 가격은 공판 실적 기반 참고 정보이며 실제 거래가를 보장하지 않음"
- 운영 주체 및 문의 채널
- 라이선스
- 개인정보 처리 방침 — **웹 푸시 구독 정보를 저장하는 순간 필수**

## 3. SEO 단독 유입의 실현 가능성 🔴

유입 경로가 SEO 하나뿐이면, SEO 실패 = 제품 실패다. 현재 상태에서는 그대로 두면 실패할 가능성이 높다.

### 3-1. 구조적 문제

| 문제 | 현황 | 영향 |
|------|------|------|
| CSR 전용 SPA | Vite + React Router, SSR·프리렌더 없음 | 크롤러가 JS 실행 후에야 콘텐츠 인식. 색인 지연·누락 |
| 라우트 2개뿐 | `/`, `/data-analysis` | 색인 가능한 페이지가 사실상 2개. 검색어 대응 폭이 극히 좁음 |
| 초기 HTML 비어 있음 | 데이터가 IndexedDB 로딩 후 렌더 | 검색 결과 스니펫에 내용 없음 → 클릭률 저하 |
| 메타·OG·sitemap | 미확인 (README에 언급 없음) | 공유 미리보기·색인 기본 요건 미충족 |

### 3-2. 검색어와 페이지의 불일치

실제 검색어는 **"송이 시세", "송이 가격", "송이 공판", "봉화 송이 시세", "울진 송이 가격 2026"** 형태의 지역 결합형이다.
현재는 이 모든 검색어가 랜딩 1개(`/`)로 수렴한다. 지역별 페이지가 없으면 롱테일 검색어를 전부 놓친다.

> 제안: **지역·조합별 정적 페이지 생성.** `/region/봉화` 형태로 빌드 시 프리렌더. 데이터가 이미 빌드 타임에 통합되므로(`generate-complete-dataset.ts`) 정적 생성 비용이 낮다. 조합 20여 개 → 색인 대상 페이지 20배 증가.

### 3-3. 타이밍이 가장 위험하다

- "송이 시세" 검색량은 **9~11월에만** 발생. 12~8월은 사실상 0.
- 신규 도메인 색인·순위 안정화에 통상 수주 소요.
- → **8월 안에 색인되어 있어야 첫 시즌 검색량을 받는다.** 9월에 시작하면 시즌 절반을 흘려보낸다.

이것이 남은 1개월에서 가장 촉박한 항목이다.

### 3-4. 퍼널 설계 부재

SEO → 방문 → **구독** 전환이 이 제품의 성장 루프인데, 이 연결이 설계되지 않았다.

```
검색 "봉화 송이 시세"
  → 지역 페이지 (즉시 가격 노출 — 여기서 이탈해도 가치는 전달됨)
  → "매일 가격 올라오면 알려드릴까요?" 구독 유도  ← 현재 존재하지 않음
  → 푸시 수신 → 재방문 (SEO 없이 반복)
```

핵심은 **구독 유도 시점**이다. 진입 즉시 권한 요청은 40~70대에서 거절률이 매우 높다. 가격을 확인해 가치를 체감한 뒤(스크롤 후 또는 2회차 방문) 노출해야 한다.

## 4. 알림 기능 스펙 초안

문답 결과 범위가 명확해졌다. 원래 로드맵의 "2주+, 조건부 임계값 알림"보다 훨씬 작다.

### 4-1. 범위

| 항목 | 결정 |
|------|------|
| 트리거 | 새 공판 데이터 게시 감지 (수집 파이프라인이 신규 날짜 데이터 확보 시) |
| 구독 단위 | 지역 / 조합 (다중 선택) |
| 날짜 조건 | **불필요** — "매일 게시 이벤트"에 흡수됨 |
| 임계값 설정 | **불필요** — 사용자 요구는 "올라왔음"이지 "얼마 이상"이 아님 |
| 메시지 | "봉화 조합 10/12 공판 결과가 등록됐습니다 — 1등급 OO만원" (가격을 메시지에 포함하면 열지 않아도 가치 전달) |
| 부가 | 시즌 시작 알림 (비시즌 구독자 재유입용) |

구독 UI는 체크박스 몇 개 수준. 이미 `useSettingsStore`에 `myRegion`/`myUnion`이 있어 기본값을 채울 수 있다.

### 4-2. 아키텍처 영향 — 백엔드가 처음 필요해진다

현재는 정적 배포(Vercel) + GitHub Actions뿐이라 **서버 상태가 없다.** 웹 푸시는 다음을 요구한다:

| 필요 요소 | 수단 |
|-----------|------|
| Service Worker | PWA 등록 (현재 없음) |
| VAPID 키 | 환경변수 관리 |
| 구독 엔드포인트 저장소 | Vercel Postgres / KV 등 — **첫 영속 저장소** |
| 구독 등록·해지 API | Vercel Functions |
| 발송 트리거 | 수집 Action이 신규 데이터 감지 시 발송 함수 호출 |
| 만료 구독 정리 | 410 응답 시 삭제 |

**동반 의무**: 구독 정보는 식별 가능한 데이터 → 개인정보 처리 방침 필요(2장과 연결). 보관 기간·삭제 방법 명시.

### 4-3. iOS 제약 — 타깃과 정면 충돌 ⚠️

웹 푸시는 iOS에서 **홈 화면 추가(PWA 설치) 후에만** 동작한다(iOS 16.4+).

- 주 타깃 40~70대에게 "공유 → 홈 화면에 추가" 안내는 허들이 매우 높다
- iPhone 사용자 비중이 낮지 않다
- Android Chrome은 브라우저에서 바로 동작

> 대응 제안:
> 1. Android 우선 완성 — 여기서 구독 루프를 검증
> 2. iOS는 **설치 안내 화면**을 별도 제공 (스크린샷 포함 3단계 안내)
> 3. iOS 미설치 사용자에게는 **앱 내 "새 데이터" 배지**로 폴백 (푸시 없이도 재방문 시 즉시 인지)
> 4. 구독 UI에 "이 기기에서 알림 가능 여부"를 먼저 판정해 노출

## 5. README 자체의 결함

### 5-1. "실시간" 표현이 실제와 다름 🔴

README 20행: "시즌 중(9~11월)에는 **실시간** 공판 현황을 제공합니다."

실제 지연 = 원본 게시 지연 + 수집 주기 최대 1시간 + 프로덕션 캐시 1시간 + 배포 시간 → **최악 2시간 이상**.
40~70대 사용자에게 "실시간"은 문자 그대로 받아들여진다. 알림 기능이 붙으면 기대치는 더 높아진다.

> 정정: "최신 공판 현황(약 1시간 주기 갱신)" + 화면에 기준 시각 상시 노출(`DataDateBadge` 이미 구현됨).

### 5-2. 미완성 기능이 보이지 않음 🟠

README만 읽으면 완성도 100%로 보인다. 실제 미구현: 알림, 차트/테이블 내보내기, 조합 단위 비교.

**날씨 연동은 진행 확정** — 근거는 사용자 수요가 아니라 세 번째 목적(본인 분석)이다. 다만 그 근거가 문서에 없어 로드맵과 단절돼 보였다. README·`CLAUDE.md`에 목적 자체를 추가하면 해소된다. 설계는 9장.

### 5-3. 지역 목록 오류 🟡

`src/const/Common.ts` 와 불일치:

| 문제 | README | 코드 (정상) |
|------|--------|-------------|
| 강원에 "의성" 포함 | `강원: [..., "삼척", "의성"]` | `강원: [..., "삼척"]` — 의성은 경북 |
| 오타 | `"예청"` | `"예천"` |

SEO 전략을 택한 이상 이건 단순 오타가 아니다. **지역별 페이지를 만들 때 오류가 그대로 색인된다.** 도메인 신뢰도에도 직접 영향(현지 사용자는 "강원 의성"을 바로 알아본다).

경남이 "거창" 1개뿐인 이유(원본 데이터 한계인지 수집 범위 한계인지)도 각주 필요.

### 5-4. 접근성 성과가 문서화되지 않음 🟡

README는 "40~70대를 위한 가독성·접근성 최적화"를 목적으로 선언하지만 구체적 내용이 0줄이다.
실제로는 큰글씨 모드(CSS 변수 스케일 + D3 폰트 연동), 라이트/다크 테마, 모바일 정보 밀도 최적화가 완료됐다. **차별점인데 검색 결과에도, 문서에도 안 드러난다.**

### 5-5. 문제 정의·차별점 부재 🟠

README는 "시세를 시각화한다"는 수단으로 시작한다. 1장에서 확인된 진짜 문제("들어가 봐야만 안다")가 문서 어디에도 없다.
SEO 관점에서도 손해다 — 이 문장이 곧 검색 스니펫이자 전환 카피다.

> 제안 (상단 3줄):
> - **문제**: 송이 공판가는 매일 바뀌는데, 사이트에 직접 들어가야만 알 수 있다.
> - **해결**: 내 지역 공판 결과가 올라오면 알림으로 알려준다.
> - **더하기**: 2013년부터의 데이터로 추이·비교까지 한 화면에서.

## 6. 초기 로딩 전략 🟠

첫 방문 시 통합 데이터셋 ~3.7MB(압축 140~234KB) 다운로드.

압축 크기는 합리적이나, 기획 관점의 문제는 **1순위 사용자가 안 쓰는 데이터를 진입 시점에 받는다**는 것이다.

- 채취자가 원하는 것: 오늘 + 내 지역 = 수 KB
- 실제: 2013년~현재 전체 파싱 + IndexedDB 쓰기
- 환경: 산지·시장 = 음영지역, 저속 회선, 구형 단말

SEO 유입이 붙으면 더 중요해진다. **검색으로 들어온 첫 방문자의 이탈률이 곧 검색 순위에 반영**되고, 이 사용자들은 캐시가 없는 상태다.

> 제안: `today.json`(또는 `latest-7d.json`) 경량 파일 선행 로드로 대시보드 즉시 렌더 → 통합 데이터셋은 백그라운드 수신. 분석 페이지 진입 시에만 전체 데이터 요구. 지역별 정적 페이지(3-2)와 결합하면 자연스럽게 해결된다.

## 7. 데이터 파이프라인 운영 공백 🟠

알림 기능이 붙으면 파이프라인 신뢰도가 곧 제품 신뢰도가 된다.

| 공백 | 위험 | 대응 |
|------|------|------|
| 수집 실패 감지 없음 | 원본 사이트 구조 변경 시 조용히 중단 | Action 실패 알림 (본인 수신) |
| "거래 없음" vs "수집 실패" 구분 없음 | 시즌 중 장애를 휴장으로 오인 → 신뢰 붕괴 | 매니페스트에 `lastCollectedAt`/`status`, 기준일 노후 시 경고 배지 |
| 오탐 푸시 위험 | 잘못된 데이터로 알림 발송 시 **취소 불가** | 발송 전 검증(Zod 스키마 + 전일 대비 이상치 체크) |

푸시는 되돌릴 수 없다. 알림 착수 전 이 항목이 선행돼야 한다.

## 8. 성공 지표

첫 시즌 = 검증 시즌. GSC + 익명 애널리틱스로 측정 가능한 최소 세트:

| 지표 | 의미 | 첫 시즌 목표(안) |
|------|------|------------------|
| 검색 노출·클릭 (GSC) | SEO 전략 작동 여부 | 시즌 중 주간 노출 1,000+ |
| 지역 페이지 색인 수 | 롱테일 확보 | 8월 말까지 20+ |
| 알림 구독 전환율 | 코어 밸류 검증 | 방문자의 10%+ |
| 구독자 재방문율 | 리텐션 루프 작동 | 푸시 발송당 30%+ |
| 첫 화면 도달 시간(3G) | 산지 실사용 가능성 | 3초 이내 |
| 분석 페이지 필터 적용률 | 분석가 실사용 여부 | 방문 중 50%+ |

**가장 중요한 단일 지표: 구독 전환율.** 이것이 낮으면 알림 가설 자체가 틀린 것이고, 높으면 다음 시즌 전략이 명확해진다.

## 11. 남은 판단 사항

- **문서 정정**: `README.md`·`CLAUDE.md`에 세 번째 목적(본인 데이터 분석)을 명시할 것인지. 명시하지 않으면 앞으로도 날씨 같은 항목이 "근거 없는 기능"으로 오판된다

- **iOS 폴백 수준**: 설치 안내만 vs 앱 내 배지까지 구현
