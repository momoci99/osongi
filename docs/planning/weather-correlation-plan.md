## 1. 목적과 성격

### 왜 하는가

이 작업의 근거는 **사용자 요구가 아니라 프로젝트의 세 번째 목적**이다.

> **개발자 본인이 송이 공판 데이터를 분석하기 위한 도구.**

`README.md`·`CLAUDE.md`에는 (1) 대시보드 제공 (2) 시즌 알림 (3) 분석 기능 제공 세 가지만 적혀 있고, "본인의 분석"이라는 목적은 문서화되어 있지 않다. 이 때문에 기존 로드맵에서 날씨 연동이 "근거 없는 항목"으로 취급됐다.

**→ 선행 조치: `CLAUDE.md` 프로젝트 목적에 본인 분석 트랙을 명시할 것.**

### 다른 트랙과의 관계

| 트랙 | 성공 기준 | 일정 제약 |
|------|-----------|-----------|
| 사용자 제품 (대시보드·알림·SEO) | 구독 전환율, 재방문율, 검색 노출 | 9월 시즌에 종속 |
| **기상 분석 (본 문서)** | **새 인사이트가 나오는가** | **없음 — 데이터 전량 소급 가능** |

두 트랙은 자원만 경합하고 일정은 경합하지 않는다. 제품 UI 이식은 분석 결과가 나온 **뒤에** 판단하는 조건부 작업이다.

## 2. 도메인 배경

송이는 기상 조건에 민감하고, **반응에 시차가 있다.** 이 시차가 분석 설계의 핵심 변수다.

```
8월 하순~9월 강수  ──(약 2주 시차)──▶  발생·출하량 증가  ──▶  공판 물량 증가  ──▶  가격 하락
지열 하강 (임계 온도 부근)  ──▶  발생 개시  ──▶  시즌 시작 시점 이동
가을 고온·가뭄 지속  ──▶  발생 부진  ──▶  물량 감소  ──▶  가격 급등
```

여기서 관측 가능한 것은 **가격·거래량**이고, 발생량 자체는 직접 관측되지 않는다.
**공판 거래량을 발생량의 대리 변수(proxy)로 쓰는 것**이 이 분석의 기본 전제다. 이 전제의 한계는 6장 참조.

## 3. 가설

| # | 가설 | 종속변수 | 설명변수 | 표본 | 우선도 |
|---|------|----------|----------|------|--------|
| **H1** | **강수 후 N일 뒤 출하량이 증가한다** | 일 거래량(kg) | 누적 강수량 (시차 N) | 800~900 | **1순위** |
| H2 | 출하량과 단가는 역상관 | 등급별 단가 | 일 거래량 | 800~900 | 2순위 |
| H3 | 시즌 개시일은 기온 하강 시점과 연동 | 첫 공판일 | 일평균/최저기온 | 13 | 탐색용 |
| H4 | 시즌 총 물량은 8~9월 강수 총량과 상관 | 시즌 총 거래량 | 8~9월 누적 강수 | 13 | 탐색용 |

### 표본 수를 먼저 인지할 것

- **일 단위(H1·H2)**: 13시즌 × 시즌당 60~70일 ≈ **800~900건** → 통계적으로 다룰 수 있음
- **시즌 단위(H3·H4)**: **13건** → 상관계수가 나와도 신뢰 불가. 시각화·서술 수준까지만

**→ H1에 집중.** H1의 시차 N을 데이터로 찾아내는 것이 이 분석의 1차 목표다.

### H1 구체화

- 시차 N을 0~30일 범위에서 스윕하며 상관을 계산 → **최대 상관을 주는 N** 탐색
- 단일 일자 강수보다 **누적 강수(3일·5일·7일 창)** 가 더 적합할 가능성이 높음 (발생은 단발 강우가 아니라 토양 수분 축적에 반응)
- 기온 조건과의 교호작용 고려: "기온이 임계 이하로 내려간 뒤의 강수"만 유효할 수 있음 → 조건부 분석 필요

## 4. 데이터

### 4-1. 소스

| 데이터 | 소스 | 소급 확보 | 보유 기간 |
|--------|------|-----------|-----------|
| 관측 (기온·강수·습도) | 기상청 ASOS/AWS 일자료 — 공공데이터포털 / 기상자료개방포털 | ✅ | 지점별 관측 개시부터 |
| 단기예보 (동네예보) | 기상청 단기예보 조회서비스 | ✅ | **2008-10-30 17:00 KST ~ 현재** |
| 공판 실적 | 기존 파이프라인 `public/auction-data/complete-dataset.json` | ✅ | 2013~ |

**전량 소급 가능** → 시즌 중 실시간 아카이빙이 필요 없다. 예보 기반 예측 모델을 만들더라도 학습 데이터를 나중에 확보할 수 있다.

### 4-2. 호출 한도 ⚠️

13시즌 × 20여 지점 × 일 8회 예보를 한 번에 긁으면 공공데이터포털 기본 일일 트래픽 상한에 걸린다.

- 수집 스크립트는 **재개 가능(resumable)** 하게 설계할 것 — 어디까지 받았는지 체크포인트 저장, 중단 후 이어받기
- 며칠에 나눠 실행하는 것을 정상 경로로 상정
- 관측 일자료는 예보보다 호출량이 훨씬 적으므로 먼저 확보

### 4-3. 저장 위치

기존 공판 데이터와 분리한다.

```
public/auction-data/     # 기존 — 제품이 로드하는 데이터
data/weather/            # 신규 — 분석 전용, 제품 번들에 포함하지 않음
  observations/YYYY.json
  forecasts/YYYY/...
  station-map.json
```

**`public/` 에 두지 말 것.** 제품 클라이언트가 받을 이유가 없고, 초기 로딩 용량 문제(검수 문서 6장)를 악화시킨다. UI 이식이 확정된 뒤에 필요한 집계 결과만 가공해 `public/`으로 내보낸다.

## 5. 관측지점 매핑

조합 20여 개를 기상 관측 지점에 대응시켜야 한다. 분석 품질을 좌우하는 실무 문제.

### 5-1. ASOS 부족 → AWS 병용

주요 산지(봉화·청송·삼척 등) 상당수는 종관관측(ASOS) 지점이 없고 방재관측(AWS)만 존재한다. AWS는 관측 요소가 적고(강수·기온 위주) 결측이 잦다.

**매핑표(`station-map.json`)에 기록할 항목:**

| 필드 | 내용 |
|------|------|
| `union` | 조합명 (예: 봉화) |
| `region` | 지역 (경북) |
| `stationId` / `stationType` | 지점번호 / ASOS·AWS |
| `distanceKm` | 조합 소재지 ~ 지점 거리 |
| `elevationDiff` | 지점 고도와 인근 산지 고도 차 (추정) |
| `available` | 사용 가능한 관측 요소 (강수/기온/습도/일조) |
| `note` | 결측 특성 등 |

### 5-2. 고도 차이 — 가장 큰 오차원 ⚠️

송이 발생지는 산지 고지대인데 관측소는 대부분 읍·면 평지에 있다. 고도 500~800m 차이면 기온이 3~5℃ 낮다.
**평지 기온으로 "지열 임계 하강 시점"을 판정하면 체계적으로 어긋난다.**

완화책:

- 절대 기온 대신 **편차·추세**를 사용 (평년 대비 편차, 전주 대비 하강폭)
- 고도 보정 상수는 검증 수단이 없어 과적합 위험 → 초기에는 도입하지 않음
- **강수량은 고도 영향이 상대적으로 작다** → H1(강수→물량)이 H3(기온→개시일)보다 신뢰도가 높다. H1을 1순위로 두는 근거가 하나 더 있는 셈

### 5-3. 공판 조합 ≠ 채취 위치

공판장에 나온 송이가 그 조합 관할 산에서 났다는 보장이 없다. 원거리 반입이 섞이면 지역 매칭이 흐려진다.
**해소 불가능한 한계**이므로 분석 결과에 반드시 명시한다. 지역을 넓게 묶어(경북 북부 등) 분석하면 완화된다.

## 6. 전제의 한계

| 전제 | 한계 | 대응 |
|------|------|------|
| 공판 거래량 = 발생량 대리 변수 | 채취자 수, 가격 기대에 따른 출하 조절, 공판장 휴장이 섞임 | 휴장일 제외, 요일 효과 확인 |
| 조합 = 채취 지역 | 원거리 반입 | 지역 단위로 묶어 완화 |
| 관측소 = 발생지 기상 | 고도차 (5-2) | 편차·추세 사용 |
| 13시즌이면 충분 | 시즌 단위 가설은 표본 13 | H3·H4는 탐색 수준으로 제한 |

## 7. 진행 순서 — UI를 먼저 만들지 말 것

가장 흔한 실패 경로: 날씨 차트 UI를 먼저 만들고 → 데이터를 붙였더니 상관이 없음 → 만든 것이 전부 낭비.

```
1. 관측 데이터 확보 + 지점 매핑표 작성
        ↓
2. 예보 데이터 확보 (분할 실행)
        ↓
3. 노트북/스크립트 탐색 분석  ← H1의 시차 N과 상관 강도를 찾는다
        ↓                      (웹 UI 없이. Python/R이 압도적으로 빠름)
4. 게이트 판정 (8장)
        ↓
5. 통과한 가설만 D3 차트로 제품 이식
```

3단계에서 아무것도 안 나오면 **5단계를 안 하는 것이 정답**이고, 그래도 본인 분석이라는 목적은 이미 달성된 것이다. 이 순서면 제품 코드에 리스크가 전혀 없다.

`public/auction-data/complete-dataset.json` 이 이미 공개 정적 파일이므로 노트북에서 바로 로드 가능하다. **별도 내보내기 기능 없이 3단계 착수 가능.**

## 8. 이식 게이트 — 무엇이 나와야 제품에 넣는가

기준을 미리 정해두지 않으면 "약한 상관"을 붙잡고 UI를 만들게 된다. 사전 고정:

| 조건 | 기준 |
|------|------|
| 상관 강도 | H1에서 시차 N에 대해 **\|r\| ≥ 0.3** 수준 이상 |
| 유의성 | p < 0.05 (다중 시차 스윕이므로 다중비교 보정 고려) |
| 재현성 | **홀드아웃 검증** — 2013~2022로 N을 찾고 2023~2025에서 재현되는가 |
| 설명 가능성 | 도메인 상식(2주 내외 시차)과 크게 어긋나지 않을 것 |

**홀드아웃이 핵심.** 시차 0~30일을 스윕하면 우연히 상관이 높은 N이 반드시 나온다. 별도 기간에서 재현되지 않으면 이식하지 않는다.

## 9. 제품 이식 시 노출 범위 ⚠️

게이트를 통과해도, 사용자에게 보여줄 때는 성격이 달라진다.

| 표현 | 판단 |
|------|------|
| "지난 시즌들에서 강수 후 약 2주 뒤 물량이 늘었습니다" — **과거 관계 서술** | ✅ 안전 |
| "이번 주 강수량 OOmm (평년 대비 +30%)" — **사실 표시** | ✅ 안전 |
| "다음 주 가격 하락 예상" — **미래 예측 수치** | ❌ 위험 |

예측을 노출하면 사용자가 **출하 시점을 미루는 등 금전적 판단**을 하고, 빗나가면 실제 손실이 발생한다. 검수 문서 2장의 면책 조항만으로는 부족하다.

> **권장: 사용자 노출은 과거 관계 서술과 사실 표시까지. 미래 시점 예측 수치는 본인 분석 트랙에만 둔다.**
> 예측을 노출하기로 결정한다면 별도 면책 + 적중률 실적 공개가 전제되어야 한다.
